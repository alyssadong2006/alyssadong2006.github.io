MY WORKFLOW / SOFTWARE ENGINEERING

How I work
with AI.

AI helps me investigate, plan, implement, and review. A local software factory keeps that work organised. I stay responsible for the scope, the behavior, and what gets published.

This is a walkthrough of the factory-guided approach I use, not a claim that AI can ship software unsupervised. The diagrams group the documented stages to make them easier to follow. The example task is illustrative, and no private work tickets or code are reproduced here.

01 / THE BIG PICTURE

A workflow, not a black box

I don’t want a tool to produce a pull request and ask me to trust it. I want to understand what changed, why it fits the request, what was checked, and what still needs a decision.

The software factory is a local coordinator around AI agents and engineering tools. It keeps the task brief, plans, code changes, reports, evidence, and open questions together. It tracks the next unfinished step instead of treating every conversation as a fresh start.

A pull request (PR) is a proposed code change that teammates can review before it is merged. The factory helps prepare that proposal; it does not replace the people reviewing it.

An agent is an AI session given a particular job and a limited set of tools. The coordinator decides which job can run next. An agent’s answer is an output to inspect, not permission to publish or proof that the work is correct.

The point is not to approve every small engineering choice. Routine work can move forward within the authorised scope. I step in when there is a real ambiguity, a new product or design decision, a missing prerequisite, or a checkpoint that needs my approval.

02 / BEFORE THE FIRST EDIT

Give the task a clear shape

A useful request says more than “fix this.” I start with the intended behavior, what happens today, the relevant context, and the boundaries of the change. That gives the agent something concrete to investigate and gives me a way to judge the result.

Goal
What should the user be able to do when the task is finished?
Evidence
Which code, reproduction steps, design references, or documentation explain the problem?
Boundaries
What must stay unchanged? Which decisions need clarification rather than a guess?
Verification
Which behaviors and edge cases would show that the change works?

The planner reads the relevant implementation and existing conventions before suggesting a fix. It should distinguish what it actually found from what it is assuming. A linked document that cannot be accessed is missing context, not a reason to invent its contents.

A separate plan review then challenges the risky parts: does the proposal solve the right problem, respect shared contracts, account for accessibility, and avoid unnecessary changes? This is a focused review of the plan, not a second attempt to investigate the entire repository.

A question should be specific. I want to know what was checked, what is still missing, why it matters, and what the agent recommends. “Should I continue?” is less useful than a clearly explained tradeoff.

For real code work, the factory uses an isolated Git worktree, which is a separate working folder attached to the same repository. That keeps task edits away from the main working folder. It is useful organisation, but it is not an operating-system security sandbox.

03 / DIVIDING THE WORK

Different jobs, different permissions

I find it more useful to give an agent a clear responsibility than to ask one session to research, code, judge itself, and publish everything. Each role produces a deliverable for the next step.

Planner

Investigates the task and proposes a complete, scoped plan. Its planning job is read-only; a finished plan does not mean the implementation has happened.

Plan reviewer

Challenges the plan and checks risk-critical assumptions. It identifies genuine blockers without reopening questions that have already been answered.

Implementer

Makes the code changes within the task’s scope and existing conventions. It can also address concrete, authorised findings from review or checks.

Code reviewer

Reads the real changed code and looks for defects, regressions, and missing coverage. A separate session adds another perspective, but AI review is still fallible.

Scenario author

For automated mobile evidence, prepares a bounded capture scenario from the task and testing conventions. Web automation instead requires an explicitly authorised observational scenario.

PR writer

Turns the verified changes and recorded results into a title and description. It should report failures, skipped checks, and limitations honestly, not turn them into a success story.

These roles are not all simultaneous writers. The coordinator limits active work per task and keeps shared preview and capture resources coordinated. A reviewer finding something does not give every agent permission to edit the same branch.

Tool access matters as much as instructions. Asking a model not to push is weaker than withholding push tools from it. Publication is a guarded coordinator operation, not something the implementer or automated task chat can authorise.

04 / WHAT COUNTS AS EVIDENCE

Check the code and the behavior

Code review, local checks, and behavior verification answer different questions. A reviewer may spot a logic problem. Tests can check expected behavior, type checks can catch mismatched data types, and lint can flag code-quality problems. Trying the actual interface can reveal something neither of them covered.

The factory runs scoped local validation through the repository’s configured targets. “Scoped” is important: checking the projects that own the changed files does not prove that every dependent project or every user journey is covered. I still need to think about the risk and choose additional checks when appropriate.

For UI changes, before-and-after evidence connects the code to something observable. The baseline must come from the original comparison revision, not from the already-edited folder. After evidence must correspond to the current changes. Screenshots help with appearance; a recording or explicit behavior check is more useful for focus, navigation, or motion.

  • Mobile: the workflow supports iOS and Android capture, subject to the required devices, environment, and scenario being available.
  • Web: manual evidence or skipped capture is the default. Automatic browser evidence needs a separately authorised, bounded observational scenario. It is not permission to submit transactions or perform arbitrary writes.
  • No UI: a task can skip screenshots and rely on appropriate checks and diff review. A decorative screenshot would add little evidence.

Manual captures remain manual. Importing an image and attesting to its revision does not independently prove where it came from, and it should never be described as an automated test. Simulated evidence from a dry run is also labelled as simulated.

A passing check has a scope. It shows that a particular check passed for particular inputs. It does not prove the whole feature is correct, and a capture by itself is not a behavioral assertion.

I review whether the final behavior matches the request before approving verification. That approval is local behavior confirmation. It is not a GitHub review approval and does not grant permission to publish.

05 / KEEPING THE DECISIONS SEPARATE

Verified does not mean published

Once the required review, checks, and behavior confirmation settle, the factory prepares the pull-request metadata and a publication checkpoint. I can inspect the branch, full diff, plans, reports, evidence, checks, and exact title and description together.

The checkpoint can be reviewed through the dashboard or the confirmed interactive terminal path. Automated task chat cannot grant publication or mark-ready approval. If the source or reviewed metadata changes before approval completes, the old checkpoint is no longer sufficient.

The same distinction applies to communication. Preparing a reply or a message is not sending it. A draft should only claim a fix or passing checks when the published changes and recorded results support that statement.

A manual override is a deliberate exception, not another route to a green badge. Skipped or failed stages must remain disclosed, and publishing still needs a fresh review and explicit confirmation. An override is not permission for a force push, merge, or deployment.

06 / THE PART THAT ISN’T A STRAIGHT LINE

Repair the problem, then check again

A review finding can be a concrete defect inside the original scope, a new product or design decision, or a request for clarification. Those should not all trigger the same response. An authorised defect can return to implementation; a new decision needs a focused human question.

Not every repair needs to rerun every command. The factory can reuse certain passing project-and-target results only after validating their declared inputs, dependency information, configuration, tools, and comparison base. A reused result is labelled not re-run. It is not a new test execution, and unprovable reuse falls back to ordinary checks.

Visual evidence has its own rules. Prior captures are not silently relabelled as new. When eligible, re-attesting them is a separate human decision about whether they still represent the current work. Otherwise the affected behavior needs fresh captures.

Failures also need honest treatment. An unrelated failure does not automatically become a pass, and deciding to continue despite it is different from fixing it. Agent attempts and repair loops have limits so that stalled work does not keep consuming time or editing indefinitely.

Pausing stops further dispatch; it does not undo partial edits or an external operation that already started. If publication times out, I inspect the branch and PR before retrying because the operation may already have taken effect. An unknown outcome is not proof of failure.

After teammate feedback, follow-up changes use the existing task and open PR when its identity still matches. The new code goes through review, verification, and checks again before an explicitly approved update. Old comments stay tied to the revision they reviewed.

07 / MAKING THE PROCESS CONCRETE

An example: verifying a UI change

Suppose I’m updating the project cards on this portfolio to make their titles, descriptions, and links easier to read on a phone. The cards might look better in a screenshot, but I also need to know that the content still fits and the interactions still work.

This is an illustrative walkthrough of how I would structure that task, not a record of a completed factory run.

From a layout change to a verified result

  1. Define what should change. Improve spacing and text hierarchy on small screens. Keep every project’s wording, technology tags, and destination links unchanged. Mission details should still expand, filters should still work, and the page should not scroll sideways.
  2. Investigate and plan. Read the card markup, shared styles, responsive rules, and interaction code. Propose a focused layout change, then have the plan reviewed for unintended effects on desktop and other cards.
  3. Capture the original UI. Use the original comparison revision, not the folder after it has been edited. Capture the same project cards on a narrow phone-sized viewport and a desktop viewport, including a card with its mission details open. For a web task, use manual captures or an explicitly authorised observational browser scenario.
  4. Implement and review the diff. Make the scoped changes. Check that the diff adjusts the intended layout without removing content, changing URLs, or rewriting unrelated interaction logic. Run the appropriate local checks.
  5. Compare like for like. Capture the updated UI with the same viewport sizes, project content, selected filter, and expanded state. Check title wrapping, paragraph readability, tag placement, link visibility, and clipped content. The after captures must correspond to the current changes.
  6. Try the interactions. Open and close mission details, switch filters, and check that each project link still has the correct destination. Use the keyboard to reach the controls and confirm that focus is visible. Check touch scrolling and browser zoom as well as the static layout.
  7. Review the evidence myself. Decide whether the layout actually makes the cards easier to read and whether the behavior matches the request. If a long title or expanded card still breaks the layout, return for a scoped fix and fresh checks of the affected behavior. A good-looking screenshot is not enough to approve the result.
  8. Prepare the PR and approve separately. Include representative before/after evidence and state which checks and interactions were actually tested. Disclose anything that was skipped or unavailable. Only then review the exact publication checkpoint, approve publishing the draft, and separately decide when it is ready for reviewers.

What would convince me? The same cards are easier to read at both sizes, their content is intact, and the filters, links, and expandable details still behave as expected. The screenshots show the layout; the interaction checks support the behavior.

The agent helps make and inspect the change. My job is to judge whether it improves the UI without breaking something else, and to make sure the evidence supports what we say in the PR.

08 / WHAT I STILL NEED TO THINK ABOUT

Useful assistance, not certainty

AI can miss a caller, misunderstand a requirement, write a plausible but incorrect test, or share the same blind spot as another agent. A second model’s confidence is not independent proof. I still need to read the diff and understand the behavior well enough to explain it.

Permissions and provenance reduce some risks; they do not remove them all. Worktrees do not sandbox repository code, screenshots can contain sensitive information, and connected tools are only useful when access and context are actually available. I keep secrets and private data out of prompts and inspect evidence before sharing it.

The factory also has boundaries. Local adapters, device availability, authentication, and browser support can block a task. A dry-run walkthrough is useful for learning the process, but simulated results do not demonstrate that a live integration worked. Proposed remote handoffs or team integrations should not be described as already available.

For me, the value is having a process I can follow and inspect: smaller responsibilities, explicit outputs, and clear decisions. AI helps with the work. It does not take responsibility for the software away from me.

A few terms, in plain language

Diff
The actual additions, deletions, and changes compared with a chosen starting revision.
Baseline
The original revision and behavior used as a reference for the proposed change.
Dry run
A simulated walkthrough of the workflow, without real model calls, product edits, device operations, or publication.
Worktree
A separate working folder for a branch in the same Git repository. It separates edits, not OS privileges.
Artifact
A saved output such as a plan, check report, screenshot, or recording that can be inspected later.
Approval gate
A checkpoint where a specific human decision is required before the next guarded action.
Source fingerprint
An identifier derived from the relevant source snapshot, used to detect changes. It says which code was checked, not whether that code is correct.
Provenance
The record of where an output came from, which revision it belongs to, and whether it was automated, manual, simulated, rerun, or reused.
